8. Pacer-прокси в SSH Connect
==============================

Что это и зачем
---------------
Hermes Agent на VPS ходит к провайдеру (например, Google Gemini по бесплатному
API). У бесплатных ключей жёсткий лимит — Gemini: 60 запросов в минуту.
Один запрос агенту это десятки LLM-вызовов подряд (сборка контекста + петля
инструментов + финальный ответ), поэтому при сложной задаче лимит выбивается
быстро. Агент получает ошибку 429 и по кругу пишет «нужно подождать минуту»,
задача буксует часами.

Pacer-прокси решает это честно и без взлома лимитов: он встаёт между hermes
и провайдером и НЕ пропускает больше 60 запросов в минуту. Запрос сверх окна
никому не вырезается и не переписывается — он просто ждёт свободный слот и
потом уходит как есть. Провайдер никогда не видит лишнего запроса, значит
никогда не отвечает 429, и агент не ждёт «минуту» по кругу.

Как работает
------------
Обычно:  hermes ────  https://generativelanguage.googleapis.com  (прямой доступ)

С пасером: hermes ──── http://127.0.0.1:17901  ────  тот же провайдер
                      (пейсер-прокси на VPS,   честный upstream
                       ограничение 60 req/мин)

Прокси это один файл на чистом стандартном Python3 (http.server + http.client):
никаких pip-пакетов на сервере ставить не нужно. Body и заголовки запроса он
передаёт дальше без изменений (кроме служебных hop-by-hop), кавычки базового
адреса провайдера при первом включении сохраняются в pacer.conf.

Файлы на VPS (в ~/.hermes подключённого пользователя)
-----------------------------------------------------
  ~/.hermes/pacer_proxy.py     сам прокси (разворачивается из кода приложения)
  ~/.hermes/pacer.conf         исходный адрес провайдера: upstream=https://...
  ~/.hermes/pacer_proxy.log    журнал прокси (старты, прошедшие запросы, ошибки)

Pacer-прокси в коде проекта
---------------------------
  web-desktop/backend/hermes_pacer.py  модуль:
    PACER_SCRIPT         исходник прокси (разворачивается на VPS через base64)
    PACER_PORT = 17901   порт (не пересекается с 17850 обратного доступа!)
    PACER_RPM  = 60      лимит скользящего окна: запросов в 60 секунд
    build_pacer_ensure_command()  команда: развернуть / поднять / переключить
                                  base_url hermes на прокси
    parse_pacer_state()           разбор PACER_UPSTREAM/PACER_PORT/
                                  PACER_RUNNING/PACER_CFG из вывода команды

Изменения конфигурации hermes (делает команда ensure):
  1) читает текущий адрес провайдера:  hermes config get model.base_url
  2) сохраняет host в ~/.hermes/pacer.conf (upstream=...)
  3) поднимает прокси nohup-ом, если он не отвечает на http://127.0.0.1:17901/_health
  4) ТОЛЬКО если прокси жив: hermes config set model.base_url http://127.0.0.1:17901
     (если прокси не поднялся — конфиг не трогается, запросы идут напрямую)

Запуск и индикация
------------------
Прокси поднимается автоматически, сам, без ручных действий:
  - перед КАЖДОЙ отправкой сообщения агенту (/api/hermes/send);
  - по кнопке-точке в веб-интерфейсе: POST /api/hermes/pacer (этот же вызов
    чинит прокси, если он упал);
  - страница чата опрашивает его каждые 45 секунд.

В тулбаре веб-чата Hermes (страница /hermes) слева от статуса подключения
находится индикатор пасера:
  ⚪ — нет данных (проверка не прошла);
  🟢 — прокси работает, запросы идут через него;
  🔴 — прокси не запущен.
При наведении показывается: состояние, порт, base_url и upstream.
Клик по точке — проверить/перезапустить прямо сейчас.

Диагностика
-----------
  - Точка в веб-чате (см. выше).
  - На VPS вручную:
      curl -s http://127.0.0.1:17901/_health     →  ok
      hermes config get model.base_url            →  http://127.0.0.1:17901
      cat ~/.hermes/pacer.conf                    →  upstream=https://...
      tail ~/.hermes/pacer_proxy.log              →  журнал прокси
      ss -ltn | grep 17901                        →  слушает ли порт

Откат / выключение пасера
-------------------------
  На VPS (в KiTTY или веб-терминале):
    hermes config set model.base_url <старый адрес>   # см. содержимое pacer.conf
    rm ~/.hermes/pacer.conf
    rm ~/.hermes/pacer_proxy.py
  Прокси на 17901 погаснет после этого сам (перезагружаться он не будет).

Настройка
---------
  Лимит и порт задаются константами в web-desktop/backend/hermes_pacer.py:
    PACER_RPM  — сколько запросов пропускать в минуту (по умолчанию 60);
    PACER_PORT — порт прокси (по умолчанию 17901, не совпадает с 17850).
  После правки констант перезапустите веб-сервер: при следующей отправке
  прокси развернётся заново и подхватит новые значения.

Важные замечания
----------------
  - Прокси идемпотентен: повторные запуски ничего не ломают, /_health проверяется
    при каждом вызове, перезапуск только если прокси мёртв.
  - base_url переключается только ПОСЛЕ успешного старта прокси — если что-то
    пошло не так, запросы остаются на прямом доступе к провайдеру.
  - Безопасность: ключ API провайдера не покидает loopback VPS — прокси и hermes
    живут на одной машине, наружу прокси ничего не открывает.
  - Пасер честный: число вызовов не «упаковывается» и не сокращается, задачи
    лишь перестают валиться в лимит — это разрешено условиями API.
  - Работает с любым HTTP-провайдером (Gemini, OpenRouter и т.п.), а не только
    с Gemini: upstream берётся из актуального model.base_url.
